# Quilnaの Apple ネイティブ試作

[English](README.md) | [日本語](README.ja.md)

Swift 6 の共有 Core と SwiftUI を使う macOS / iOS の最小アプリです。
Swift向け外部パッケージには依存せず、SQLite 3.54.1の公式Cソースを同梱します。
macOS／iOSで同じFTS5と修正済みWAL実装を使用し、動的拡張の読込みは無効にします。
取得元・ライセンス・照合済みハッシュは`Sources/CSQLite/PROVENANCE.json`に記録します。
最低対象は macOS 14 / iOS 17 です。
Appleの端末内翻訳にはmacOS 15 / iOS 18以降と、対応する言語データが必要です。

## 利用できる内容

- 「情報収集」と「教科書」のタブ切替。
- HTTPSのRSS 2.0／Atomフィードの追加・購読解除、起動時・前面復帰時・手動の更新。
- 原文の記事・要約、ブックマーク、取得失敗時も残るSQLiteキャッシュ。
- Apple Translationによる日本語訳と保存。原文と訳文を分けて表示し、保存失敗時は訳文を保持して再試行。
- 日本語の固定教材「モデルとエージェント」全 3 節、目安 5〜10 分。
- 目次、読書、各節 1 問の選択問題、選択理由に対応した解説。
- 教材 ID と版を分けた SQLite 回答履歴、アプリ再起動後の読込。
- 保存失敗の表示と回答の画面内保持、保存の再試行。
- 壊れた履歴・未知の保存形式を自動初期化しない処理。

正誤表示は各問題への回答結果です。理解全体や定着を判定したとは表示しません。
AIによる教材生成と端末間同期は未接続です。
任意の HTML / JavaScript や、モデルが生成したコードを実行しません。

## 情報収集と翻訳

「Apple Developer ニュースを追加」で実際の公式RSSを購読できます。
任意のフィードはHTTPS URLを入力します。認証情報を埋め込んだURLは受け付けません。
更新条件にETag／Last-Modifiedを使い、記事のIDを維持して保存します。
表示する本文はフィードに含まれる記事・要約であり、元サイトの全文取得は行いません。
収集はアプリの起動・前面復帰・手動操作で実行します。常時巡回のサービスは未実装です。

原文・ブックマーク・日本語訳はこの端末に保存します。
一覧は最新2,000記事と保存済みブックマーク（最大2,000件）を統合します。
検索欄はこの一覧上限とは独立して、SQLiteに保存された全記事を対象にします。
原文のタイトル・要約・本文と、現在の原文に対応する保存済み日本語訳のタイトル・本文を検索します。
フィードまたはブックマークの絞り込みは50件の取得上限より前に適用し、
結果は保存・更新された順です。「さらに50件を読み込む」で同じ順序の続きを取得します。
検索結果から、通常一覧の2,000件より古い記事も原文と保存済み日本語訳を含む詳細を開けます。
購読を解除しても、保存済みのブックマーク記事は残します。
翻訳は記事ID・翻訳対象の原文・対象言語を対応付け、古い原文への翻訳結果で新しい訳を上書きしません。
原文が更新された場合、古い原文に対応する日本語訳は検索にも詳細にも現在の訳として表示しません。

検索語はUnicode空白で区切った最大8語をAND条件として扱い、正規化後128 Unicode scalarまでです。
各語は意味を推測せずリテラルな部分一致で検索します。全角・半角、ひらがな・カタカナ、
ASCII英字の大文字・小文字は同一視しますが、音声・表記ゆれなどの意味的な推論は行いません。
TAB、改行、CRLF、NEL、全角空白も区切りです。1文字と2文字の検索語にも対応します。

翻訳ボタンを押すと、必要な場合にOSの言語ダウンロード画面が開きます。
macOS 26.4／iOS 26.4以降では`lowLatency`を明示します。翻訳用の外部LLM APIは使いません。
iOS SimulatorではAppleの翻訳処理が利用できないため、その旨を表示します。
ただし、すでに保存されている現在の日本語訳は、SimulatorおよびmacOS 14／iOS 17でも表示します。
RSS・ブックマークと教材の検証はSimulator、実翻訳の検証はMacで行います。

Xユーザーの投稿を直接取得する機能は未接続です。
LocalRSSは既存のRSSを保存するプラグインで、Xからの取得には別のプロバイダーが必要です。
X Premiumの契約をX APIの無料利用枠とは扱いません。X認証・API購入は自動で行いません。

## macOS で実行

Swift / Xcode の導入済み環境を使います。依存の追加取得はありません。
試験用の保存先を明示すると、既存の Application Support に書き込みません。

```bash
swift run --package-path apple \
  --scratch-path /private/tmp/quilna-swift-build \
  --cache-path /private/tmp/quilna-swift-cache \
  Quilna --data-directory /private/tmp/quilna-native-qa
```

通常起動で保存先を指定しない場合は、アプリの Application Support 配下の
`TsumikiText/answers.sqlite`と`TsumikiText/feed-library.sqlite`を使います。
Quilnaへの改名後も既存データを利用できるよう、この保存先とBundle IDは維持します。
フィード取得は購読先へ通信します。秘密情報やAPIキーは扱いません。
試作には DB 暗号化・App Sandbox・署名・公証の配布設定はまだありません。
Swift のメモリ安全性は、これらの OS の権限・配布設定の代替ではありません。

ローカル確認用の未署名 `.app` は次で生成します。

```bash
sh apple/scripts/build-macos-app.sh
open apple/.build/native/Quilna.app --args \
  --data-directory /private/tmp/quilna-native-qa
```

成果物は `apple/.build/native/` です。
App Store 配布物や Developer ID 署名済みアプリではありません。

## iOS Simulator 用ビルド

`apple/Quilna.xcodeproj` の共有 scheme `Quilna-iOS` が
同じ `TextbookUI` と `TextbookCore` をローカル Swift Package として使用します。

```bash
xcodebuild -project apple/Quilna.xcodeproj \
  -scheme Quilna-iOS -configuration Debug \
  -sdk iphonesimulator -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath /private/tmp/quilna-ios-build \
  CODE_SIGNING_ALLOWED=NO build
```

ビルド成功と Simulator / 実機での操作確認は別に報告します。
実機へのインストール・署名・Apple アカウントの設定は行いません。

## 自動検証

```bash
swift test --package-path apple \
  --scratch-path /private/tmp/quilna-swift-build \
  --cache-path /private/tmp/quilna-swift-cache
```

回答の永続化、教材版の分離、同一回答の再保存、異なる内容による上書き拒否、
書込失敗と再試行、破損データの保持、保存中の目次移動を検証します。
RSS／Atomの文字コード・実体参照・リンク解決、保存後の再読込、
購読解除中の取得、翻訳キャッシュの遅延応答、原文更新と訳文保存の接続間競合も検証します。
日時は `Date.timeIntervalSinceReferenceDate` の秒を SQLite の REAL に保存し、
小数秒を含む日時を別の基準時刻へ変換して丸めないようにします。

## DB読取の100ms予算

ローカル記事DB（`feed-library.sqlite`）への呼び出し開始からSwiftの結果取得までを
100ms未満にすることを性能要件とします。
平均値だけで判定せず、各操作30回の初回・反復測定の最大値が100ms以上なら不合格です。
SQL実行、結果の文字列・URL・日時への変換、actorへの実行待ちを計測に含めます。

```bash
mise run apple:benchmark
# JSONを保存する場合（出力先の親ディレクトリは事前に用意する）
sh apple/scripts/benchmark-db.sh /absolute/path/result.json
```

専用の一時DBに10万記事・100購読・古い1万ブックマークを作り、release構成で次を測定します。
記事には日本語を含む約2KBの本文と要約、同日時・日時なしのデータを含めます。

- 最新記事2,000件、フィード別記事1,000件、古いブックマーク2,000件の取得。
- 100購読の取得、ブックマーク判定、原文に対応する日本語訳の取得。
- 画面用の購読・最新記事・ブックマークの3クエリをまとめた取得。

結果には各測定値、初回、p50／p95／p99、最大値、OS・SQLiteの版を出力します。
データ件数を減らす、結果本文を省く、検索結果をキャッシュで代用する方法で合格させません。
個人の保存DBは使わず、測定終了後に合成データを削除します。

現在の基準測定は書込み競合のない状態が対象です。DB接続・整合性検査・初期インポート、
ネットワーク取得、翻訳の実行、画面描画は別の時間として扱います。
OSのページキャッシュは消去しないため、初回測定をディスクの完全なコールド読取とは呼びません。
同じactor内の長い書込みによる待ち時間と、物理iPhoneでの上限は別途検証が必要です。
全文検索にも同じ100ms予算を適用し、次の専用ゲートでより厳しい書込み競合条件を確認します。

## 全文検索の100msゲート

全文検索の専用ゲートは、約2KBの原文10万件と、それぞれに対応する約2KBの
新鮮な日本語訳10万件を作成します。固定された検索条件を、通常時、公開APIの
`beforeCommit`で未コミット書込みを保持した状態、継続的に原文・訳文を書き込む状態で
各30回測定します。最初のAPI呼出し、actorの待機、50件の本文・訳文をSwift値へ
完全に展開する時間を含み、すべての標本が厳密に100ms未満であることを要求します。
継続書込みでは15回目と16回目の検索の間に、期限付きで実コミットを1回待ち、各30回の検索区間内でwriterの進行を成立させます。
この同期は検索時間に含めず、writer停止、書込み例外、期限超過は不合格とします。
各区間内に成功コミットの時刻が入ることも検証し、正常なコミット1回より先に高速な検索が終わった場合をwriter停止と誤判定しません。
標本には並行writerの処理も含むプロセス全体のCPU時間も記録します。診断用であり、実時間の判定を置き換えたり、I/Oと実行待ちを区別したりする値ではありません。
`TSUMIKI_SEARCH_KEEP_FIXTURE=1`を指定すると、原因調査のため合成DBを保持し、専用の一時パスを`diagnosticDatabaseDirectory`へ記録します。
保持するDBは数GBになる場合があり、調査後に削除できます。通常実行では合成DBを自動削除します。

```bash
sh apple/scripts/benchmark-search.sh
# JSONを保存する場合
sh apple/scripts/benchmark-search.sh /absolute/path/result.json
```

初回の索引作成と既存記事のバックフィルは「検索索引の準備」であり、上記の検索測定とは
別です。ゲートはオラクルとの一致、全ページ走査、検索対象本文の保持も確認し、候補の先行上限、
結果キャッシュ、外れ値の除外は行いません。物理iPhoneやすべての端末・負荷に対する
普遍的なハードリアルタイム保証ではありません。

2026-10-22のMacでの先行測定では、通常時・書込み競合中・全ページ走査の計6,197回が
すべて100ms未満で、最大47.35msでした。継続書込みは7,170回のコミットを確認しています。
初回バックフィルは約82秒で、検索時間とは別に記録します。
その後の検証では未コミット書込み保持中に198.56msで失敗し、その標本も除外せず保存しています。
専用readerは64MiBのページキャッシュと最大2,147,418,112バイトのメモリマップを要求し、
SQLiteの実効上限に従います。接続単位のI/O設定であり、検索結果のキャッシュではありません。
効果は同じ変更していないゲートで検証します。マップ上限は仮想アドレス空間であり、常駐RAMの一括確保ではありません。
物理iPhoneのメモリ使用量と性能は引き続き測定が必要です。
全測定値と検証状況は、Git管理外の
`.local-state/fulltext-search/2026-10-22/report.json`と`search.json`に保存しています。
最終macOS／iOS Simulatorバイナリで合成データを使った検索の画面操作確認が通りました。
原文・訳文、古い記事の詳細、かなの同一視、絞り込み、消去、ページ送り、エラー、孤児ブックマークの削除を含みます。
物理iPhoneの性能は未測定です。

ネイティブ画面遷移の回帰確認手順は、検索、検索終了、サイドバーへ戻る、ブックマークを選ぶ、
そこで検索と消去を行う、全記事へ戻って再検索する、の順です。ゼロ件・エラー状態や詳細表示の往復後も、
記事一覧の検索欄を操作できることを確認します。iOSはナビゲーションバーの検索欄を常時表示する配置を明示し、
macOSは自動配置を維持します。実際の画面確認で見つかったフィルター遷移の不具合を対象にした手順であり、
ビルド成功だけではこの動作を確認したことにはしません。

## 保存基盤と検索エンジンの選定

SQLiteは現在の実装上の選択です。要件は、対象端末と負荷で正しい検索結果を100ms未満で返すことであり、SQLiteの継続利用自体は要件ではありません。
予算を満たせない場合は、クエリ・索引・接続構成の改善、専用検索索引の導入、DBの変更を、同じデータ・競合条件・結果の正しさ・計測範囲で比較します。
macOSと物理iPhoneで、オフライン動作、メモリ・保存容量、索引準備、安全性、運用費も含めて代替案を測定します。
必要に応じて保存と検索の部品を分けて選びます。切替前に、データ移行、原文・訳文・ブックマーク・回答履歴の保持、ロールバックを検証します。
開発ハーネスの台帳は別の部品です。記事・検索用の保存基盤を変更しても、台帳まで一律に変更する必要はありません。

## 構成

- `Sources/TextbookCore`: フィード解析・HTTP取得、記事・訳文・回答モデル、SQLite保存。
- `Sources/TextbookUI`: macOS / iOS共通の情報収集・教材画面、端末内翻訳、保存状態。
- `Sources/Quilna`: macOS の起動点、試験用の保存先引数。
- `iOS`: iOS の起動点。
- `Tests`: Core と保存中の UI 状態遷移の回帰試験。

SQLite は C 実装であり、Swift の型検査だけで内部の安全性を保証しません。
DB handle は actor から外へ出さず、SQL の値は bind して扱います。
既存の Web 試作や、教材生成 API の接続状態は変更しません。
