# 製品の開発順序

## ブラウザ版を先に完成させる

2026-10-24のプロジェクトオーナーの判断を[Issue #41](https://github.com/tqer39/quilna/issues/41)に記録しています。
まず合意した製品機能をすべてブラウザ版へ実装し、全体の使い勝手をプロジェクトオーナーが明示的に「使いやすい」と判断するまで改善を続けます。
全機能の実装完了と使いやすさの受け入れの両方を満たしてから、iOS・macOS等を1プラットフォームずつ進めます。
ブラウザ版の機能一覧はIssue #41で管理します。RSSの一部や固定教材の完成だけで製品全体の完成とは扱いません。
両方の条件を満たすまでは、macOS／iOSの機能開発、ネイティブ画面の実験、配布準備、端末性能の検証、ネイティブのモデル評価を保留します。
既存のネイティブ実装・PR・日付付きの検証結果は保持し、未完了のIssueも開いたままにします。
既存CIと必要なセキュリティ保守では、引き続きネイティブコードやGoハーネスを検証できます。

## 読む・好奇心を持つ・情報をつなぐ

実装と受け入れは、ビューアのデザインを[Issue #72](https://github.com/tqer39/quilna/issues/72)、ハイライトと情報の関連を[Issue #73](https://github.com/tqer39/quilna/issues/73)で追跡します。

2026-10-27のプロジェクトオーナーの優先順位の明確化により、製品の中心をRSSリーダーとニュース・SNSフィードの購読に置きます。
翻訳と読み上げは読むことを支える機能です。画面上の操作と開発の優先順位は、記事の収集と閲覧を主にします。
翻訳先の既定は利用者のロケールに合わせ、設定画面で変更できるようにします。言語や音声の設定を、記事を読み始めるための必須操作にはしません。

以下は目指す画面構成と実装順序です。ハイライトとメモの保存、理由付きの関連記事候補、明示的な記事間の関連付けはブラウザブランチに実装しています（[リーダーガイド](browser-rss.ja.md#ハイライトとメモ)）。学ぶポイントの抽出・引用間の関連付け・関係図は計画段階で、実装完了と利用者の使いやすさの受け入れは区別します。

| 段階 | 中心となる体験 | 受け入れ条件 |
| --- | --- | --- |
| 購読して読む | 主なナビゲーションに購読先・未読記事・配信元の絞り込み・検索・保存記事を置き、記事本文を中心に表示します。 | 情報源の追加から新着の発見・閲覧・保存・再開まで、学習や音声の操作に入らず使えます。本文未取得・収集失敗・未対応の情報源を明示します。 |
| 気になることを見つける | 本文を選択してハイライトと短いメモを保存できます。学ぶポイントや問いの候補を、本文のそばに少数提示します。 | 候補から根拠となる本文と出典へ移動できます。候補を非表示にして読み続けられ、問題への回答や教材化を強制しません。 |
| 読んだ情報をつなぐ | 保存した箇所や過去に読んだ記事を、共通の概念・参照・利用者が作ったつながりなどの理由とともに提示します。 | 根拠の確認・関連の修正や削除・該当箇所への移動ができます。提案された関連と利用者が確認した関連を区別します。 |
| 関係を眺めて辿る | 記事・ハイライト・概念を起点に、周辺の関係図を開き、必要なつながりを広げます。 | 関係を選ぶと理由と出典を確認できます。同じ内容を一覧とキーボード操作でも辿れ、記事を読むために大きな関係図の操作を要求しません。 |

ニュースとSNSの購読は同じ収集体験に含めますが、対応範囲は情報源ごとに明示します。
RSS/Atomがあれば利用し、認証・API・料金が必要なサービスは、アダプターと前提条件を整えるまで未接続として扱います。
任意のSNSのURLを貼れば継続購読できるような表示にはしません。

学びの支援は、利用者が選んだ本文・メモ・明示的なリンクから始め、その記録を使って根拠付きの候補と関係図を追加します。
記事の識別情報・引用した本文・出典の版を保持し、記事の再取得や翻訳表示でハイライトや根拠の位置を無断で移動しないようにします。
共通タグだけから提案できるのは関連する話題であり、記事どうしが支持・反証し合うという事実関係ではありません。
推定した関係は候補として表示し、根拠となる本文を残して、利用者が非表示にできるようにします。
未読・既読、保存、ハイライト、利用者が明示的に記録した学習の状態を分けます。記事を開いただけでは、学習・理解したとは判断しません。
ブラウザ内での翻訳を優先する既存方針を維持し、記事本文を外部の解析・翻訳サービスへ送る前に、別途方針を決めます。

最初の実装単位は閲覧とハイライトの保存、次に根拠付きの関連記事カード、その次に起点を絞った関係図とします。
各段階をブラウザで利用者に確認してもらいます。教材化は選んだ情報をさらに深く学ぶ任意の経路として後からつなぎ、読了後の既定の行き先にはしません。
読み上げの改善は、閲覧を妨げたり保存データを危険にさらしたりする不具合の修正を除き、この優先順位を押しのけないようにします。

## 受け入れまでの反復

1. ブラウザで、購読・記事一覧・記事閲覧・保存・再開から確認します。次にハイライト・学びのきっかけ・根拠付きの関連・関係図を確認します。その後に、選んだ出典から任意の教材化・目次や図・問題と解説・学習の保存と再開をつなぎます。
2. アプリやソースの版、ブラウザ・表示幅、プロジェクトオーナーの具体的な感想を記録します。
3. 使い勝手を妨げる問題を再現・修正し、影響する動作を検証してから、変更した流れを再度試してもらいます。
4. 合意したブラウザ機能をすべて実装し、明示的な使いやすさの受け入れまで改善を続けます。完了と受け入れた範囲を記録してから、ネイティブを1プラットフォームずつ進めます。

自動テスト・CI・ベンチマーク・モデルレビューは検証の補助であり、プロジェクトオーナーの使いやすさの判断を代行しません。
教材・版の識別情報と個人の回答履歴を保持し、実際の保存失敗には再試行の手段を示します。
実キー入力・認証・実際の教材生成など、実装済みの動作と模擬操作・未接続の機能を区別します。
固定のサンプル教材だけで、教材生成を含む製品全体が完成したとは扱いません。

## 作業の優先順位

- [セキュリティ保守](security-maintenance.ja.md)を含む、安全性とデータ消失の問題を優先します。
- ブラウザの使いやすさと具体的な感想はIssue #41で扱います。[情報収集の入口 #48](https://github.com/tqer39/quilna/issues/48)を先に確認し、任意の機能追加より利用を妨げる問題の修正を優先します。
- 上記の購読と閲覧、続いてハイライトと根拠付きの関連を優先します。[Issue #7](https://github.com/tqer39/quilna/issues/7)の出典から教材・理解問題までの流れは、さらに深く学ぶ任意の経路としてブラウザ版で進めます。
- 出典を保つ共有は[Issue #30](https://github.com/tqer39/quilna/issues/30)、論文の収集は[Issue #31](https://github.com/tqer39/quilna/issues/31)として、学習体験に続く課題に保持します。
- ネイティブ専用の作業は、合意したブラウザ機能がすべて完成し、プロジェクトオーナーが受け入れるまで保留します。

この順序の変更は、有料API呼び出し、新しい認証情報、公開、無関係なPRのマージを許可するものではありません。
ブラウザ版の受け入れは現在未完了です。実装報告や自動検証の成功から受け入れ済みとは判断しません。
