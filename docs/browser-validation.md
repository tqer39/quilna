# Browser development validation

[English](browser-validation.md) | [日本語](browser-validation.ja.md)

Use the browser checks for the current product phase. A successful check does not replace independent source review or the owner's usability acceptance in [the product sequence](product-development.md).

## Maintained checks

With the pinned Node runtime and installed lockfile dependencies, run from the checkout root:

```bash
mise exec -- npm run check:browser
```

This serial entry point stops on the first failure: `npm run lint` → `npm test` → `npm run build` → `npm run test:browser` → `npm run test:reader-runtime` → `npm run test:search-performance`.
Lint includes documentation and security-policy checks; build includes the TypeScript check. The individual commands remain available for targeted repair and fixed harness stages. This command does not install dependencies, invoke models, push, deploy, or build native apps.
Chromium must already be installed with the maintained Playwright version; installation is an explicit setup step (`npm exec --no -- playwright install chromium`).
Live vulnerability scanning remains separate (`npm run security:audit`), with registry signatures, dependency review and Go scanning in the existing workflows. Workers changes also require the existing Workers build/tests.

The functional suite owns `127.0.0.1:5197` and the performance suite owns `127.0.0.1:5199`. Both start Vite from the config's checkout, use `--strictPort`, and reject an already-running server. Never enable `reuseExistingServer` to work around a conflict: determine who owns the port and wait or stop only your own test process. The user's preview on port 5192 is separate.
Playwright uses disposable contexts, and fixtures populate only synthetic data in their own origin/profile. The server test suite also briefly reserves both test ports to check that unrelated servers are rejected before any test executes. Do not run it concurrently with either browser suite. Authentication/provider responses are mocked by the relevant tests. This is not live account, synchronization, translation-quality or physical-phone acceptance.
See the official [web-server behavior](https://playwright.dev/docs/test-webserver) and [JSON reporter](https://playwright.dev/docs/test-reporters#json-reporter).

The reader runtime suite builds fresh browser assets and serves them over loopback HTTPS on an ephemeral port. It uses real Better Auth, D1 and SQLite-backed Durable Objects, with only Google and publisher responses replaced by offline fixtures. Two disposable browser profiles exercise login, RSS subscription, shared extraction/reuse, separate saved/read state, version updates, failed refresh, permission withdrawal, restart and retained offline history at desktop/mobile widths. The test-only entry permits two synthetic accounts and gates assets; it does not replace the production asset-gate tests or establish live sharing acceptance. Unexpected browser/Worker outbound requests are rejected.

The runtime comparison waits for the article to render, reads its committed browser version and inline article copy, and compares both with an authenticated server read of that exact version ID. Two profiles must retain identical immutable versions and original timestamps while saved/read flags remain separate and the publisher is fetched only once. The acquisition response status is still checked; acquisition `reused` flags are checked in the Workers transport tests. This avoids making Chromium's separate response-body observer authoritative for application persistence.

## Evidence and repair

Functional test results are written to `test-results/browser.json`, with failure traces under `test-results/chromium/`. Reader runtime results are in `test-results/reader-runtime.json`, with screenshots and retained failure traces under `test-results/reader-runtime/`. Search test results are in `test-results/search.json`, with all measured samples in `.local-state/search-performance/results/**/measurements.json`.
These paths are overwritten by later invocations. Before repair or another run, retain failed logs and copy the relevant JSON/traces to an ignored, task-specific directory. Record the exact commands, runtime/browser versions, source hash and dependency identity. A Git commit alone is insufficient for a dirty checkout; retain a hash manifest covering changed and untracked source/config/test files too.

Use [the reader guide's search contract](browser-rss.md#local-article-search) without weakening its 200 ms gate, reducing its samples or discarding outliers. Initial database loading and preparation are separate. The baseline corpus has no tags; a separate dense-tag variant preserves the same text corpus and adds tag queries/filters. Neither measures a physical phone.
On failure, distinguish a product defect, a test-control defect and a missing prerequisite. Preserve the failure, fix its cause, and rerun affected checks. Reuse a prior successful check only when its source, controls, dependencies, environment and retained evidence still match. Do not repeat runs just to obtain a pass.

The CI web job runs the same maintained functional, reader runtime and search commands after its existing static/unit/build checks. It records the checked-out SHA and uploads the synthetic test results and measurements for 14 days, including failures after validation starts. The upload paths exclude personal databases and general `.local-state` contents. A missing or failed check is not an acceptance, even if an artifact upload succeeds. Native/Go jobs and the required workflow result are not removed by this change.

The [b65abf8 CI run](https://github.com/tqer39/quilna/actions/runs/40995944241) failed a cloud-queue fixture after 523 functional passes. Its trace recorded the seed page starting a read after the fixture published a queue, then cancelling it on reload; the next page read the same item. The fixture now waits for the initial empty-queue status before publishing the queue. Exact read-count assertions remain unchanged; the original failed result is retained.

On 2026-10-30, [b4ab3b0 CI](https://github.com/tqer39/quilna/actions/runs/41008948201) passed 556 functional cases but failed one of four runtime cases when Playwright `response.json()` could not retrieve the acquisition body through Chromium's protocol. Search did not run. A diagnostic that kept the original failing assertion did not reproduce it in 20 macOS cases, then reproduced it in one of five Linux x64 container cases. In that failure, the app displayed and retained the original and its version, with one publisher fetch. The original CI trace and diagnostic failure remain retained. The comparison above checks those application outcomes directly against authenticated server state; it does not claim to fix the underlying Chromium protocol behavior.

### Inspect downloaded CI evidence

After downloading one `browser-validation-<run>-<attempt>` artifact into a separate directory, use the read-only verifier:

```bash
node scripts/verify-browser-evidence.mjs ARTIFACT_DIR CHECKED_OUT_SHA FUNCTIONAL_COUNT RUNTIME_COUNT
```

Supply the full checked-out commit SHA and expected case counts from the intended source/test inventory, not from the artifact's success counters. For the 2026-10-30 run `41011410353`, these arguments were `28afde9041b369ab5f95ed85e6910a87268cd9b4 556 4`. A PR run can check out a temporary merge commit; separately verify its tree against the intended HEAD before reusing its evidence. The verifier checks the artifact's recorded SHA, not GitHub's run identity, tree equivalence or provenance. Use a trusted download from the exact run/attempt and verify that workflow's conclusion independently. A fabricated or consistently replaced report cannot be authenticated by this script.

It rejects missing/invalid reports, zero tests, mismatched counts/projects, duplicate cases, skipped/flaky/expected-failure results, retries, and report-level errors. It checks every individual result rather than trusting aggregate counters. Search requires all three designs with both corpora, the maintained corpus sizes and tag density, 30 samples for every query/filter and contention condition (2,700 total), successful writer timestamps, a matching raw maximum and every sample strictly below 200 ms. Missing preparation timings or measurement files also fail. Workload or reporter-format changes require deliberate verifier/test updates; unknown conditions do not silently pass.

Success writes a JSON summary to stdout with separate preparation timings, all six maxima, case counts and SHA-256 hashes of the ten inspected files. Failure exits nonzero without a success summary. It does not run or retry tests, alter artifacts, fetch credentials, make network requests or approve a PR. The regression tests run through the existing `npm test` and CI server suite. Correctness assertions, per-query writer progress and coverage still depend on the maintained benchmark and source review; an evidence summary is not a new performance measurement, security audit, independent review or owner acceptance.

### Search diagnostics

When a search failure needs timing detail, run `node scripts/diagnose-search.mjs` after preserving the original failure. This creates an instrumented copy of the maintained benchmark under a new `.local-state/search-diagnostics/run-*/` directory; it does not edit the benchmark, application or acceptance results. It uses the same isolated port/profile and runs all 630 dense-tag samples for each design, retaining correctness, writer-progress and 200 ms assertions. It is a diagnostic experiment, not acceptance: tracing adds overhead, and the untagged baseline is not run.

The optional arguments select a design and CPU slowdown, for example `node scripts/diagnose-search.mjs editorial 4`. Allowed designs are `all` (default), `studio`, `editorial`, and `focus`; slowdown is `1` (default), `2`, or `4`. These are local experiments, not claims about equivalent physical devices. Do not run this alongside browser/server tests that own the same ports.

The copy records synchronous input-dispatch time, the remaining paint/correctness time, first-frame callback time, visibility/focus at both ends, and a compressed Chromium trace. Both animation-frame callbacks remain inside the measurement. Trace categories cover renderer work, GC, top-level tasks, compositor/Viz and renderer scheduling so a delayed frame can be distinguished from long application work. A Paint event alone does not prove that pixels were presented; see Chromium's [life of a frame](https://github.com/chromium/chromium/blob/main/docs/life_of_a_frame.md). The manifest records source/dependency/control hashes and the generated copy; completion reports whether source hashes stayed unchanged and every expected trace is complete. Inspect `diagnosticError` and `traceDataLoss` before interpreting a trace. Compressed traces are capped at 128 MiB each; a partial or missing trace is diagnostic failure, never evidence that no pause occurred. Source-adapter drift fails explicitly rather than silently changing the workload. Only synthetic fixtures are profiled; no personal profile, credentials or account data are copied. See [Playwright CDP sessions](https://playwright.dev/docs/api/class-cdpsession).

If the maintained search gate fails in CI, its normal artifact is uploaded first. A separate four-minute diagnostic step then uses the default slowdown of 1, with traces in `search-diagnostics-<run>-<attempt>` retained for 14 days when the job is not cancelled. The original failure remains a failure even if diagnostics pass. The web job has a 25-minute total limit for installation, checks and diagnostics: a recorded dependency installation alone took 12m33s and exhausted the former 15-minute job budget during functional tests. This does not change the 200 ms search limit or per-test limits. Cancellation can prevent diagnostic upload, while already-uploaded normal evidence remains available.

On 2026-10-27 JST, [Linux CI at b8225d6](https://github.com/tqer39/quilna/actions/runs/40392253433) passed 252 functional tests and five search conditions; Studio's dense-tag held-write single-result query took 270.9 ms. All 2,700 samples were retained. The subsequent diagnostic captured three complete traces with no reported data loss and matching application/control/dependency hashes. Its Studio maximum was 274.8 ms: input dispatch took 1.5 ms, Paint ended around 8.5 ms, and the second frame callback arrived at 274.6 ms. Focus similarly took 204.8 ms, with Paint ending around 22.8 ms and the second callback at 204.7 ms. The narrower trace did not capture a long V8 GC event in either interval; this did not rule out other collection tasks. The expanded trace categories and visibility/focus fields above investigate that gap without changing the application, maintained gate or failed outcome.

The expanded [Linux trace at 8483204](https://github.com/tqer39/quilna/actions/runs/40395964801) identified main-thread tasks posted by `cppgc-internal/sweeper.cc` / `IncrementalSweepTask::Post` lasting 252.280 / 285.563 / 269.589 ms in Studio / Editorial / Focus. They overlap most of the diagnostic pauses (256.6 / 296.4 / 293.1 ms); dispatch took 1–3 ms and both endpoint visibility/focus readings were active. These C++ sweep tasks were absent from the earlier narrow categories. [Blink's C++ collector](https://www.chromium.org/blink/blink-gc/) is distinct from the V8-only events previously inspected. The trace identifies the blocking task, not which DOM, IndexedDB or other objects it reclaimed. All three traces were complete, reported no data loss, and matched source/control/dependency hashes. The normal gate retained all 2,700 samples and failed one Focus held-write sample at 285.7 ms, with 252 functional tests passing. Reusing connected list rows and controls addresses observed DOM churn, but whether it removes this pause requires the unchanged gate and subsequent trace evidence; the failure is not reclassified as a pass.

A same-machine Studio diagnostic after row reuse still recorded a 22.486 ms C++ sweep task (24.331 ms before); this is not evidence that the CI pause was fixed. The next controlled change bounds article reads to 500 results in a single transaction. Chromium's [IDBAny implementation](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/modules/indexeddb/idb_any.cc) retains a native array for `getAll()` results, making large-result cleanup a candidate, not a proven allocation attribution. Snapshot consistency, late failure/abort, complete IDs and storage preservation must pass before accepting this read-path change. The [IndexedDB transaction lifecycle](https://w3c.github.io/IndexedDB/#transaction-lifecycle) explains why later batches are requested synchronously during success callbacks instead of opening separate transactions.

In the subsequent local Studio comparison, manifest hashes differed only for `src/feed-store.ts`; both runs retained all 630 samples and complete traces without reported data loss. The maximum C++ sweep task changed from 22.486 to 3.240 ms and their total from 30.372 to 8.190 ms. Initial load/preparation increased from 2,452 to 2,836 ms. Diagnostic input-to-paint maxima were 49.9 and 60.3 ms, respectively: this is evidence about cleanup cost, not an across-the-board latency improvement or Linux acceptance. The unchanged gate across all designs and hosted CI remain required.

On 2026-10-30, [6a02904 Linux CI](https://github.com/tqer39/quilna/actions/runs/40998555529) passed 524 functional and two reader-runtime cases, but one of 2,700 search samples failed: Studio, dense tags, held write, `does-not-exist`, 203.5 ms. Its subsequent diagnostic retained 630 samples per design and three complete traces without reported data loss; source/control hashes remained unchanged and visibility/focus stayed active. Diagnostic maxima were Studio 62.7, Editorial 60.0 and Focus 59.1 ms. It did not reproduce the failing span, so neither a root cause nor a repair is established. The original failed gate remains failed; no threshold, workload or outlier rule was relaxed, and deployment was held.

## Existing harness integration

Use the existing [Go harness contract](../harness/README.md), not a new loop runner or an automatic-approve reviewer. Keep its frozen task, checks, distinct review execution, bounded repair, no-replay recovery and hash checks.
For a browser-only task, select the individual maintained commands above as trusted `checks`, in the same order. When relevant, add Workers checks. Each check should have its own operation/log so a failure can be passed to repair with the existing bounded diagnostics. Reserve `check:browser` for local convenience; do not also run its component commands in the same task.

The harness uses an isolated HOME and fixed PATH. Supply a trusted local wrapper with explicit absolute Node/npm paths and only the required toolchain PATH; otherwise npm's child commands may not find Node. Pass the already-installed Playwright browser cache explicitly as `PLAYWRIGHT_BROWSERS_PATH` so the disposable HOME does not trigger a missing-browser failure. Never copy credentials or personal configuration to satisfy this prerequisite. Keep the wrapper and task outside the model-editable scope and include their identity in the recorded controls. Use the harness’s `freeze-task` command to list the wrapper and relevant check/configuration files explicitly in `protectedFiles`; it verifies their content and mode at operation boundaries, including files outside the workspace code hash. This detects persistent changes, not transient edits reverted between checkpoints, and does not discover transitive dependencies. Follow the [fixed-controls contract](../harness/README.md#fixed-check-controls).

Choose allowed source paths, acceptance criteria, reviewer and operation/time/repair limits before dispatch. Do not assign check editing to repair, synthesize `approve` from test success, or infer model/spending authorization from this guide. No current browser run is independently accepted merely because the offline harness tests pass. The remaining native-oriented preparation helpers on other branches must not be imported wholesale into browser work.

Temporarily permitting server reuse caused both regressions to fail; restoring the refusal passed both. The earlier missing-document failure and unsafe-control failures were preserved.
