# Durable source document catalog

[English](source-document-catalog.md) | [日本語](source-document-catalog.ja.md)

## Implementation boundary

`DocumentCatalog` in `workers/document-catalog.mjs` is the persistent storage core for [Issue #74](https://github.com/tqer39/quilna/issues/74). The code now connects it to authenticated HTTP routes, server article extraction and an exact-source access database. The browser reader now has an opt-in authenticated acquisition client. The service is **disabled unless explicitly configured**. The live owner-only deployment has no catalog binding or sharing option and continues to use its existing reader and RSS delivery queue. Local Miniflare tests use SQLite-backed Durable Objects and real Better Auth sessions with offline Google responses; these are not live multi-user acceptance or completion of synchronization.

The host selects one storage object per authorized scope and normalized source URL and supplies trusted `authorize` and `load` adapters. An authorization decision must be exactly `true`. Scope names, document IDs and version hashes are identifiers, not credentials. Every acquisition, read and history request authorizes before looking at storage; permission is checked again after asynchronous work. Unauthorized requests return the same unavailable status whether a document is cached or not. The source object independently checks access and that its object ID matches the resolved scope/source. Test identity headers exist only in isolated fixture entries.

The loader receives only the source URL and the previous original/HTTP validators. It must acquire and extract the source on the server within a bounded time, enforce the existing public-address/redirect/response limits, and return validated original content or a matching not-modified result. Browser-supplied text must never be treated as a trusted shared source. Original content uses the same document/version IDs, representation digest, code ranges and format version as the browser. The shared format checks have no DOM dependency. Personal subscriptions, saved/read flags, translations, quotes and learning records are not catalog fields.

## Trusted article acquisition

`workers/article-loader.mjs` provides the server-owned `load` adapter. The service and local runtime fixture fetch HTML and extract it before catalog storage; they do not trust article JSON supplied by a browser or publisher. The browser and adapter share `src/article-extraction.ts` and `src/article-serialization.ts`, with [Readability](https://github.com/mozilla/readability) and a server-only [LinkeDOM worker build](https://github.com/WebReflection/linkedom#whats-new).

Acquisition uses the existing public-only HTTPS fetch boundary: no user cookies or authorization headers, blocked/self-host checks at each redirect, at most three redirects, a 12-second network deadline and a 2,000,000-byte response cap. HTTP validators go only to their exact saved final URL. A matching 304 reuses the catalog's original without parsing; a 200 response without validators clears the old validators. RSS/XML, forbidden responses and pages without an extractable body fail rather than becoming shared articles. Login-wall detection is heuristic, not an access-control or paywall classifier.

Parsing uses an inert template in a fresh DOM; no remote nodes are mounted in the browser, no source scripts are executed, no subresources are loaded, and server DOM classes are never installed on shared globals. Removed elements include active resources, forms, navigation and hidden content. The serializer returns plain text and code ranges, never source HTML. Code indentation, tabs, line breaks and decoded entities are retained. Input is bounded before Readability traversal/cloning to 20,000 elements and 256 nesting levels, with 140–200,000 UTF-16 units in the extracted body. Parsing is synchronous and these structural limits do not promise a wall-clock CPU deadline; deployment CPU limits still apply.

Fixed fixtures compare browser/server text, code ranges, title and language for full/fragment/malformed documents, Japanese/astral Unicode, tables and hostile resources. The real local Workers runtime covers HTML extraction into a chunked durable version, concurrent reuse, restart, 304 and failure/retry with the old version intact. DOM implementations may differ on other malformed pages; this is fixture evidence, not universal extraction equivalence or live-site acceptance. Dependency and lockfile are shared across development platforms; the server-only worker export adds no native runtime dependency or browser download.

## Authenticated transport and access policy

`GET /api/documents/status` returns the authenticated account and whether acquisition is configured. `POST /api/documents/acquire`, `/read` and `/history` require same-origin requests and the existing session CSRF token. Bodies contain `url`, `audience` (`private` or `shared`) and only the operation's optional `force`, `versionId` or `after` field. Browser-supplied owners, scopes, content and action overrides are rejected. `X-Document-Account`, when supplied, must match the verified account. The HTTP layer rechecks the same authenticated subject/session after asynchronous work, so logout or expiry observed then prevents delivery.

Private documents use `private:<account hash>` and cannot share versions with another account. Shared documents require an enabled, unexpired row for the **exact normalized source URL**, a delivery-permission evidence record and an explicit account membership in the separate `DOCUMENT_ACCESS_DB`. The initial schema is `migrations/documents/0001_access.sql`; only the separately enabled administrator controls below can write policies or memberships through HTTP. `shared:<policy UUID>:<revision>` isolates policy revisions. Do not infer approval from a public URL or remove queries to find a grant. Shared acquisition refuses a redirect to a different URL before fetching it; approved aliases resolve to the exact policy source before acquisition, as described below. Private acquisition retains the existing public redirect checks.

### Approved source aliases

`migrations/documents/0002_source_aliases.sql` adds operator-reviewed exact URL aliases to an existing policy ID and revision, with their own enabled flag, expiry and evidence. Apply both access migrations before using aliases. No live grants are created by the migration. Each request requires current policy membership and both unexpired permissions. Updating a policy revision invalidates old alias grants until they are explicitly reviewed again. A URL already present as any policy's primary source cannot resolve through an alias, including when that primary policy is disabled or inaccessible to this reader. There are no alias chains, query-parameter removal, URL similarity or HTML canonical-based merges.

The gateway resolves an alias to the policy source for document identity and quota reservation, but passes the originally requested URL into the document object. Both layers recheck that original URL's authorization after asynchronous work and verify the resolved scope/source still match. Removing or changing the alias during acquisition prevents delivery. Acquisition fetches only the policy source; it does not fetch the alias or authorize redirects to additional URLs. Different permitted aliases and feed GUIDs therefore share one scoped original and immutable version while subscriptions and reading records remain independent.

Alias responses include a `resolution` binding of `requestedURL`, `sourceURL` and `scope`. The browser requires that binding before accepting a different shared source; private acquisition still requires the exact requested URL. The registered article URL stays intact. Saved body history displays the registered URL and the retained original's source, and preserves access to earlier browser/private/shared copies. This is a record of an already authorized download, not a reusable authorization token. Local alias metadata, limited to 50 distinct URLs per document, is included in backup v2; reaching the limit fails without evicting existing mappings or originals. Restoring a backup does not grant server access, and later revocation does not erase downloaded copies.

### Permission rechecks and limits

Each permission lookup starts a new [D1 first-primary session](https://developers.cloudflare.com/d1/best-practices/read-replication/), including after fetch/storage work. Removing a member, disabling a policy or expiring it denies the next check. Increase the policy revision atomically with changes to source-delivery terms or reassignment; never recycle a revision or policy ID for unrelated terms. A revision change makes older scope versions unavailable through this API. Policy metadata, member lists and delivery evidence are not returned to readers. Revocation committed before the final permission check prevents delivery; later revocation cannot retract an already-authorized response or downloaded copy. D1 permission changes and Durable Object publication are not one transaction: a racing withdrawal may leave an inaccessible cached version. The outer gateway checks permission again before delivery, and session validity is checked separately. This does not promise atomic revocation across both databases.

All document POST commands use the existing persisted per-account 20-per-minute mutation limit, including reads, history and retries; another account has its own allowance. Acquisition additionally reserves up to 1,000 distinct normalized URL/audience slots per account in an atomic transaction. Repeated requests reuse a slot. Failed acquisition retains the reservation and earlier versions; the slot is not silently evicted or reset. A full account can still read/history/retry reserved sources, subject to the rate limit. Capacity and recovery controls for removing reservations are not yet exposed. Document version/byte bounds below remain separate.

Pending acquisition returns 202 with `retryAt`; clients must wait rather than poll aggressively. Denied or missing documents return 404, invalid commands 400, CSRF/account mismatches 403, rate limits 429, capacity/conflicts 409, unconfigured service 503, and other extraction/storage failures 502 without underlying errors. Responses use `no-store`. A body requires a verified session even when its source is shared.

Enabling this path requires `DOCUMENTS_ENABLED=true`, a `DOCUMENTS` binding to the exported SQLite-backed `SourceDocument` class and its Durable Object migration. Shared mode also requires a separate `DOCUMENT_ACCESS_DB` binding with the access migration and reviewed grants. No tracked deployment configuration enables it or creates those resources. Keep the current private login allowlist; adding source grants does not admit new login users. Policy administration and owner acceptance are required before a real rollout.

## Administrator policy controls

`workers/document-policy-admin.mjs` adds a guarded management API. The browser editor below uses that API; production delivery remains disabled. It requires `DOCUMENT_ADMIN_ENABLED=true`, `DOCUMENT_ADMIN_OWNER_HASH` equal to the verified account hash and `DOCUMENT_ACCESS_DB` with all four document migrations. No tracked configuration sets these values. The separate login allowlist remains authoritative; adding a document member never creates an account or admits another login user. Real source permissions still need an explicit delivery-policy decision.

`GET /api/documents/admin-status` reports availability for the current account. The POST commands `admin-list`, `admin-read`, `admin-history`, `admin-revision`, `admin-create` and `admin-update` require same origin, session CSRF and a matching `X-Document-Account` header. The HTTP layer checks the same subject/session again after reading the body, before dispatch, and after completion. All POST commands use the existing per-account rate limit. A management body is capped at 262,144 UTF-8 bytes; other document commands retain their 32 KiB bound. Non-administrators cannot list or mutate policy records, even when they can read a shared document. This API does not call a provider, fetch a publisher or enable document acquisition.

List requests contain optional `after`; read requests contain `id`. Lists return at most 20 policy metadata records and a cursor, without member/alias arrays. Create requests contain `url`, `enabled`, `expires`, `evidence`, `members` (account hashes) and `aliases`. Each alias has `url`, `enabled`, `expires`, `evidence` and its explicitly approved `policyRevision`. Update requests replace `url` with `id` and `expectedRevision` (the last read `managementRevision`). Source URLs and policy IDs are immutable. URLs use the public HTTPS normalization/host checks and retain arbitrary query parameters. Duplicate members or normalized aliases, invalid input and active expired grants are refused; active aliases cannot outlive their active parent policy. Disabled records may retain expired dates so revocation remains possible.

Migration `0003_policy_management.sql` preserves existing permissions and adds a separate management revision. Every successful edit advances it; member, expiry and enabled-state changes retain the document scope and cached versions. Changing the exact evidence text advances the policy revision too. Active aliases must explicitly approve that new revision or be disabled; legacy stale approvals are not silently reactivated. Database triggers prevent primary/alias collisions and alias chains during management writes, including across competing requests. An alias already owned by another policy cannot be reassigned implicitly.

Policy metadata, membership and aliases commit in one [D1 batch transaction](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), using a fresh first-primary session. Each dependent write is gated by a server-generated operation token from the successful revision comparison. A stale/concurrent edit cannot overwrite the winner's membership or aliases. SQL failures roll back the whole batch. The response reads the complete saved policy inside that transaction; it is not a second, potentially mixed snapshot. There are no automatic mutation retries: after a lost response or conflict, reread the policy before deciding whether to save again. Revocation affects the next acquisition authorization check, including a pending fetch; it does not erase downloaded copies or make D1 and document storage one transaction.

Management supports at most 1,000 policies, 100 members and 50 aliases per policy. Capacity reports a conflict rather than deleting permissions or immutable evidence. Disabling a policy withdraws access while retaining its identity; this API does not delete a policy, erase cached versions, reclaim source reservations or restore an earlier permission automatically. Live configuration and owner usability acceptance remain unfinished. Local runtime tests cover migration, concurrent edits, SQL rollback, alias collisions/reapproval, revocation during fetch, pagination/capacity and same-version reuse by a newly added member.

## Policy change history

`0004_policy_history.sql` adds append-only snapshots of every successful management save, with the verified administrator account hash, server time, event kind and management revision. The snapshot includes permission evidence, members and alias approvals but no article text or personal reading records. The insert shares the permission-save transaction: a history write failure rolls back the whole edit, and a losing concurrent edit records no event. Database triggers reject updates/deletes of retained events. History is not automatically pruned; storage exhaustion fails the save while preserving the prior permission. This is application history, not protection against a database administrator replacing the database.

Existing permissions are unchanged by migration. On their first successful edit, the pre-existing state is captured once as a `baseline`, with a null actor and the capture time. Earlier edits cannot be reconstructed; the UI explicitly says the original actor/time are unknown. Until that first edit, a legacy permission has no history. Baseline capture and the new revision commit together.

`admin-history` takes `id` and optional exclusive `before` management revision, returning at most 20 metadata entries in descending revision order. `admin-revision` takes `id` and `revision` and returns one complete historical snapshot. Both use the same administrator, account, CSRF and session checks as editing. Unknown records are unavailable; corrupt retained detail fails without modifying data. Readers with document permission cannot read management history. In the editor, **変更履歴を確認** opens history separately from the draft. Reading an old revision preserves the current draft and does not reinstate old members or expired grants. An account change hides the history with the rest of the management workspace. A restore/reapproval workflow remains unimplemented.

## Browser permission editor

**Settings → 共有する本文の管理（管理者用）** connects only when the administrator explicitly checks the connection. It shows the current account ID, at most 20 saved sources per page and a form for the exact source URL, enabled state, local-time expiry, permission evidence, member IDs and approved aliases. New policies start disabled, with only the current account prefilled. This does not invite users or change the login allowlist. The source URL is immutable after creation. Account IDs are identifiers, not API keys or authorization by themselves.

The administrator reviews the source, members, expiry and alias states before explicitly saving. Changes to permission evidence or an alias's URL/evidence clear its visible approval; an active alias requires an explicit confirmation under the current policy revision. Existing approval is never silently advanced. The UI uses text nodes for source-provided strings and does not fetch the entered source. It validates input locally, while the server remains authoritative for permissions and conflicts.

A new save replaces the previous success notice with its own pending state. It checks the administrator account before dispatch and again after completion; the returned policy identity, revisions and saved fields must match the submitted draft before success is shown. Network loss, conflicts or an inconsistent acknowledgement keep the draft and stop automatic or blind repeat saves. **最新の保存内容を確認** reads the current server version without replacing the draft. Replacing the draft with that saved version requires an explicit discard confirmation. After an uncertain create, inspect the source list before opening the saved source or explicitly discarding the draft to start over. A lost response may still represent a committed save.

A known login change or loss of administrator access conceals the workspace and retains the draft in memory for reconnection by the same account. Switching to another account requires explicitly discarding it. Closing the settings dialog retains an in-memory draft; leaving/reloading the page can lose it, with a browser navigation warning when supported. Drafts are not stored in localStorage, exported in library backups or synchronized. This is not browser-wide account isolation or historical operator recovery.

Browser tests cover all three designs at 320 px, keyboard access, explicit alias approval, conflict/lost-response recovery, wrong save acknowledgements and session changes. The offline runtime suite creates policies, adds a second reader and revokes that reader through the built app and real auth/D1 path; the same immutable source is reused and private reading state stays separate. These use synthetic permissions and separate profiles, not real-source grants or owner acceptance.

## Browser acquisition and local copies

In **Settings → 本文の取得・再利用**, the default remains browser acquisition. A reader can choose private cloud originals or permitted shared originals after a successful authenticated configuration check. The choice is bound to that account; selecting a different mode does not rewrite existing articles. Refresh from **本文の保存履歴** to use the newly selected source. Only the URL, audience and refresh choice are submitted, with session/CSRF/account headers; personal flags, translations, quotes and browser article text are not uploaded.

Each cloud acquisition checks configuration/account before sending and again before local retention. It accepts bounded JSON (4,100,000 bytes, 16 seconds per request), validates source/scope/IDs and representation hashes, and retains the exact immutable server version and original timestamps. A late older revision cannot rewind the local current pointer. An existing version with conflicting content/timestamps or conflicting metadata at the same revision is rejected transactionally. Changing the acquisition preference aborts pending requests and article writes; failures leave existing article content and its independent saved/read state intact. A pending response shows an explicit retry notice; there is no automatic polling or fallback to another audience/site.

The existing `quilna.documents.v1` database is upgraded in place to schema version 3: version 2 adds the source-URL metadata index, and version 3 adds a multi-entry alias index. Both version 1 and version 2 originals are retained during upgrade. Stores, IDs and version contents are preserved. The history selector reads metadata for that source and pages each original's versions in groups of 20, so browser/private/shared histories remain accessible after switching sources. Locally downloaded copies remain readable offline, including after a later permission withdrawal. This is not server-side history synchronization: only versions acquired or restored into this browser appear. Preferences are not included in library backups.

The browser library is still shared by one browser profile, not isolated per login. Use separate browser profiles for different people; logging out does not erase retained copies or personal records. This remains a prerequisite for broader multi-user rollout. Browser fixtures use separate disposable profiles. In addition to mocked-response cases and server authorization tests, the maintained reader runtime suite connects the browser to real local authentication, RSS, extraction and persistence with offline Google/publisher fixtures; see [browser validation](browser-validation.md). Neither proves live multi-user usability. Offline reading assumes the app has loaded; offline startup installation is not provided.

## Persistence and recovery

- A fresh original is reusable for 24 hours. Explicit refresh bypasses freshness. Concurrent requests receive a pending result with a retry time while one durable 30-second lease owns acquisition. The caller must retry; this core has no background worker or polling UI.
- Network and digest work runs outside storage transactions. A random lease token and its expiry are checked atomically with publishing a version and changing the current pointer. An expired or replaced worker cannot publish a late result or clear a newer lease. A new request can recover after expiry. Failed release writes leave recovery to expiry.
- Immutable versions keep their original acquisition and catalog timestamps. Unchanged revalidation updates only the current document's check/revision and validator metadata. Reverting to an earlier representation reuses its old version. Source failures, capacity failures and transactional write failures preserve earlier versions; read access remains separate from refreshing.
- Each version is serialized in 16,000 UTF-16-unit parts. Parts and the current pointer commit in one transaction. Reads verify lengths, source/scope/ID references and the representation digest. Unknown schemas and corrupt records fail without replacing them with an empty catalog. A corrupt old version cannot become current during a reversion.
- Current bounds are 100 immutable versions and 10,000,000 serialized UTF-8 bytes per document, with a 4,000,000-byte per-version bound. Hitting a bound reports capacity failure rather than silently evicting evidence. History returns at most 20 entries and a cursor based on the last version ID. It is ordered by first retention, not by last selection.

Transactions follow the [Durable Objects storage contract](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/). Runtime fixtures verify chunked persistence across disposal/restart, one acquisition for simultaneous synthetic users, conditional revalidation and private/shared scope separation. Fault-injection tests cover expired/late leases, changed and reverted representations, permission revocation during acquisition, partial write rollback/retry, count/byte capacity, pagination and corrupt/future records. These are local synthetic results, not live multi-user or browser acceptance.

## Remaining integration

Complete retention/correction/deletion and operator recovery, and obtain acceptance of the policy-management browser UI before enabling delivery. The guarded administration API, browser editor and exact alias resolution are implemented; there is no live policy administration or automatic alias approval. Live grants require reviewed source-delivery terms; synthetic test permissions are not approval for real sources. Keep the current owner-only environment unchanged until its intended sharing scope is explicitly established. Preserve offline copies and the existing browser search gate; this service does not replace browser storage.
