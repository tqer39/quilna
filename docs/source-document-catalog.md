# Durable source document catalog

[English](source-document-catalog.md) | [日本語](source-document-catalog.ja.md)

## Implementation boundary

`DocumentCatalog` in `workers/document-catalog.mjs` is the persistent storage core for [Issue #74](https://github.com/tqer39/quilna/issues/74). The code now connects it to authenticated HTTP routes, server article extraction and an exact-source access database. The browser reader now has an opt-in authenticated acquisition client. The service is **disabled unless explicitly configured**. The live owner-only deployment has no catalog binding or sharing option and continues to use its existing reader and RSS delivery queue. Local Miniflare tests use SQLite-backed Durable Objects and real Better Auth sessions with offline Google responses; these are not live multi-user acceptance or completion of synchronization.

The host selects one storage object per authorized scope and normalized source URL and supplies trusted `authorize` and `load` adapters. An authorization decision must be exactly `true`. Scope names, document IDs and version hashes are identifiers, not credentials. Every acquisition, read and history request authorizes before looking at storage; permission is checked again after asynchronous work. Unauthorized requests return the same unavailable status whether a document is cached or not. The source object independently checks access and that its object ID matches the resolved scope/source. Test identity headers exist only in isolated fixture entries.

The loader receives only the source URL and the previous original/HTTP validators. It must acquire and extract the source on the server within a bounded time, enforce the existing public-address/redirect/response limits, and return validated original content or a matching not-modified result. Browser-supplied text must never be treated as a trusted shared source. Original content uses the same document/version IDs, representation digest, code ranges and format version as the browser. The shared format checks have no DOM dependency. Personal subscriptions, saved/read flags, translations, quotes and learning records are not catalog fields.

## Trusted article acquisition

`workers/article-loader.mjs` provides the server-owned `load` adapter. The service and local runtime fixture fetch HTML and extract it before catalog storage; they do not trust article JSON supplied by a browser or publisher. The browser and adapter share `src/article-extraction.ts` and `src/article-serialization.ts`, with [Readability](https://github.com/mozilla/readability) and a server-only [LinkeDOM worker build](https://github.com/WebReflection/linkedom#whats-new).

Acquisition uses the existing public-only HTTPS fetch boundary: no user cookies or authorization headers, blocked/self-host checks at each redirect, at most three redirects, a 12-second network deadline and a 2,000,000-byte response cap. HTTP validators go only to their exact saved final URL. A matching 304 reuses the catalog's original without parsing; a 200 response without validators clears the old validators. RSS/XML, forbidden responses and pages without an extractable body fail rather than becoming shared articles. Login-wall detection is heuristic, not an access-control or paywall classifier.

Parsing uses an inert template in a fresh DOM; no remote nodes are mounted in the browser, no source scripts are executed, no subresources are loaded, and server DOM classes are never installed on shared globals. Removed elements include active resources, forms, navigation and hidden content. The serializer returns plain text and code ranges, never source HTML. Code indentation, tabs, line breaks and decoded entities are retained. Input is bounded before Readability traversal/cloning to 20,000 elements and 256 nesting levels, with 140–200,000 UTF-16 units in the extracted body. Parsing is synchronous and these structural limits do not promise a wall-clock CPU deadline; deployment CPU limits still apply.

Fixed fixtures compare browser/server text, code ranges, title and language for full/fragment/malformed documents, Japanese/astral Unicode, tables and hostile resources. The real local Workers runtime covers HTML extraction into a chunked durable version, concurrent reuse, restart, 304 and failure/retry with the old version intact. DOM implementations may differ on other malformed pages; this is fixture evidence, not universal extraction equivalence or live-site acceptance. Dependency and lockfile are shared across development platforms; the server-only worker export adds no native runtime dependency or browser download.

## Authenticated transport and access policy

`GET /api/documents/status` returns the authenticated account and whether acquisition is configured. `POST /api/documents/acquire`, `/read` and `/history` require same-origin requests and the existing session CSRF token. Bodies contain `url`, `audience` (`private` or `shared`) and only the operation's optional `force`, `versionId` or `after` field. Browser-supplied owners, scopes, content and action overrides are rejected. `X-Document-Account`, when supplied, must match the verified account. The HTTP layer rechecks the same authenticated subject/session after asynchronous work, so logout or expiry observed then prevents delivery.

Private documents use `private:<account hash>` and cannot share versions with another account. Shared documents require an enabled, unexpired row for the **exact normalized source URL**, a delivery-permission evidence record and an explicit account membership in the separate `DOCUMENT_ACCESS_DB`. The schema is `migrations/documents/0001_access.sql`; no browser endpoint writes policies or memberships. `shared:<policy UUID>:<revision>` isolates policy revisions. Do not infer approval from a public URL or remove queries to find a grant. Shared acquisition refuses a redirect to a different URL before fetching it; approved aliases are not implemented. Private acquisition retains the existing public redirect checks.

Each permission lookup starts a new [D1 first-primary session](https://developers.cloudflare.com/d1/best-practices/read-replication/), including after fetch/storage work. Removing a member, disabling a policy or expiring it denies the next check. Increase the policy revision atomically with changes to source-delivery terms or reassignment; never recycle a revision or policy ID for unrelated terms. A revision change makes older scope versions unavailable through this API. Policy metadata, member lists and delivery evidence are not returned to readers. Revocation committed before the final permission check prevents delivery; later revocation cannot retract an already-authorized response or downloaded copy. D1 permission changes and Durable Object publication are not one transaction: a racing withdrawal may leave an inaccessible cached version. The outer gateway checks permission again before delivery, and session validity is checked separately. This does not promise atomic revocation across both databases.

All document POST commands use the existing persisted per-account 20-per-minute mutation limit, including reads, history and retries; another account has its own allowance. Acquisition additionally reserves up to 1,000 distinct normalized URL/audience slots per account in an atomic transaction. Repeated requests reuse a slot. Failed acquisition retains the reservation and earlier versions; the slot is not silently evicted or reset. A full account can still read/history/retry reserved sources, subject to the rate limit. Capacity and recovery controls for removing reservations are not yet exposed. Document version/byte bounds below remain separate.

Pending acquisition returns 202 with `retryAt`; clients must wait rather than poll aggressively. Denied or missing documents return 404, invalid commands 400, CSRF/account mismatches 403, rate limits 429, capacity/conflicts 409, unconfigured service 503, and other extraction/storage failures 502 without underlying errors. Responses use `no-store`. A body requires a verified session even when its source is shared.

Enabling this path requires `DOCUMENTS_ENABLED=true`, a `DOCUMENTS` binding to the exported SQLite-backed `SourceDocument` class and its Durable Object migration. Shared mode also requires a separate `DOCUMENT_ACCESS_DB` binding with the access migration and reviewed grants. No tracked deployment configuration enables it or creates those resources. Keep the current private login allowlist; adding source grants does not admit new login users. Policy administration and owner acceptance are required before a real rollout.

## Browser acquisition and local copies

In **Settings → 本文の取得・再利用**, the default remains browser acquisition. A reader can choose private cloud originals or permitted shared originals after a successful authenticated configuration check. The choice is bound to that account; selecting a different mode does not rewrite existing articles. Refresh from **本文の保存履歴** to use the newly selected source. Only the URL, audience and refresh choice are submitted, with session/CSRF/account headers; personal flags, translations, quotes and browser article text are not uploaded.

Each cloud acquisition checks configuration/account before sending and again before local retention. It accepts bounded JSON (4,100,000 bytes, 16 seconds per request), validates source/scope/IDs and representation hashes, and retains the exact immutable server version and original timestamps. A late older revision cannot rewind the local current pointer. An existing version with conflicting content/timestamps or conflicting metadata at the same revision is rejected transactionally. Changing the acquisition preference aborts pending requests and article writes; failures leave existing article content and its independent saved/read state intact. A pending response shows an explicit retry notice; there is no automatic polling or fallback to another audience/site.

The existing `quilna.documents.v1` database is upgraded in place to schema version 2 by adding a source-URL metadata index. Stores, IDs and version contents are preserved. The history selector reads metadata for that source and pages each original's versions in groups of 20, so browser/private/shared histories remain accessible after switching sources. Locally downloaded copies remain readable offline, including after a later permission withdrawal. This is not server-side history synchronization: only versions acquired or restored into this browser appear. Preferences are not included in library backups.

The browser library is still shared by one browser profile, not isolated per login. Use separate browser profiles for different people; logging out does not erase retained copies or personal records. This remains a prerequisite for broader multi-user rollout. Browser fixtures use separate disposable profiles. In addition to mocked-response cases and server authorization tests, the maintained reader runtime suite connects the browser to real local authentication, RSS, extraction and persistence with offline Google/publisher fixtures; see [browser validation](browser-validation.md). Neither proves live multi-user usability. Offline reading assumes the app has loaded; offline startup installation is not provided.

## Persistence and recovery

- A fresh original is reusable for 24 hours. Explicit refresh bypasses freshness. Concurrent requests receive a pending result with a retry time while one durable 30-second lease owns acquisition. The caller must retry; this core has no background worker or polling UI.
- Network and digest work runs outside storage transactions. A random lease token and its expiry are checked atomically with publishing a version and changing the current pointer. An expired or replaced worker cannot publish a late result or clear a newer lease. A new request can recover after expiry. Failed release writes leave recovery to expiry.
- Immutable versions keep their original acquisition and catalog timestamps. Unchanged revalidation updates only the current document's check/revision and validator metadata. Reverting to an earlier representation reuses its old version. Source failures, capacity failures and transactional write failures preserve earlier versions; read access remains separate from refreshing.
- Each version is serialized in 16,000 UTF-16-unit parts. Parts and the current pointer commit in one transaction. Reads verify lengths, source/scope/ID references and the representation digest. Unknown schemas and corrupt records fail without replacing them with an empty catalog. A corrupt old version cannot become current during a reversion.
- Current bounds are 100 immutable versions and 10,000,000 serialized UTF-8 bytes per document, with a 4,000,000-byte per-version bound. Hitting a bound reports capacity failure rather than silently evicting evidence. History returns at most 20 entries and a cursor based on the last version ID. It is ordered by first retention, not by last selection.

Transactions follow the [Durable Objects storage contract](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/). Runtime fixtures verify chunked persistence across disposal/restart, one acquisition for simultaneous synthetic users, conditional revalidation and private/shared scope separation. Fault-injection tests cover expired/late leases, changed and reverted representations, permission revocation during acquisition, partial write rollback/retry, count/byte capacity, pagination and corrupt/future records. These are local synthetic results, not live multi-user or browser acceptance.

## Remaining integration

Provide policy administration, source aliases, retention/correction/deletion and operator recovery before enabling delivery. Live grants require reviewed source-delivery terms; synthetic test permissions are not approval for real sources. Keep the current owner-only environment unchanged until its intended sharing scope is explicitly established. Preserve offline copies and the existing browser search gate; this service does not replace browser storage.
