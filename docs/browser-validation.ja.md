# ブラウザ開発の検証

[English](browser-validation.md) | [日本語](browser-validation.ja.md)

現在の製品段階ではブラウザ用の検証を使います。検査の成功は、独立したソースレビューや[開発順序](product-development.ja.md)で定める利用者の使いやすさの受け入れを代替しません。

## 維持する検証入口

固定したNodeランタイムとロックファイルの依存を準備し、作業ツリーのルートで実行します。

```bash
mise exec -- npm run check:browser
```

この入口は `npm run lint` → `npm test` → `npm run build` → `npm run test:browser` → `npm run test:reader-runtime` → `npm run test:search-performance` を順番に実行し、最初の失敗で停止します。
lintには文書とセキュリティ方針の検査、buildにはTypeScript検査が含まれます。修正後の対象限定検証やハーネスの固定ステージには、個別コマンドを引き続き使えます。このコマンドは依存のインストール、モデル呼び出し、push、公開、ネイティブビルドを行いません。
使用するPlaywrightに対応したChromiumを事前に用意します。インストールは明示的な準備操作（`npm exec --no -- playwright install chromium`）です。
最新の脆弱性検査は別途 `npm run security:audit` で行い、既存ワークフローでレジストリ署名、依存レビュー、Goの検査を維持します。Workersの変更には既存のWorkersビルド・テストも必要です。

機能テストは `127.0.0.1:5197`、性能テストは `127.0.0.1:5199` を専有します。どちらも設定ファイルの作業ツリーからViteを `--strictPort` で起動し、既存サーバーがあれば失敗します。競合を回避するために `reuseExistingServer` を有効化せず、ポートの所有者を確認して待つか、自分の検証プロセスだけを停止します。利用者の5192番ポートのプレビューとは分離します。
Playwrightは使い捨てコンテキストを使い、専用オリジン・プロファイルの合成データだけを操作します。サーバーテストも両方の検証ポートを短時間使用し、別サーバーがあればテスト実行前に拒否することを確認します。どちらのブラウザ検証とも同時実行しません。認証・プロバイダーの応答は各対象テストで模擬します。実アカウント、同期、翻訳品質、実機スマートフォンの受け入れ確認とは異なります。
公式の[Webサーバー動作](https://playwright.dev/docs/test-webserver)と[JSONレポーター](https://playwright.dev/docs/test-reporters#json-reporter)を参照してください。

リーダーの実行環境テストはブラウザを新しくビルドし、一時ポートのループバックHTTPSで配信します。Better Auth、D1、SQLite-backed Durable Objectsは実処理を使い、Googleと配信元の応答だけをオフラインの固定データへ置き換えます。独立した2つの一時プロフィールで、ログイン、RSS購読、共有本文の抽出・再利用、保存／既読の分離、版更新、更新失敗、権限取り消し、再起動、保存履歴のオフライン閲覧をパソコン幅・モバイル幅で検証します。テスト専用の入口は合成アカウント2件と記事画面の認証を扱いますが、本番の画面認証テストや実ユーザー間の共有受け入れを代替しません。ブラウザ・Workerの想定外の外向き通信は拒否します。

実行環境の照合では記事の表示を待ち、ブラウザに確定保存した本文版と記事内の本文を、同じ版IDの認証付きサーバー読み取りと比較します。2プロフィールで不変版・元の日時が一致し、保存／既読は分離され、配信元の取得が1回であることを必要条件にします。取得応答の状態コードも確認し、取得時の `reused` フラグはWorkersの通信テストで確認します。アプリの保存成否を、Chromium側の別経路の応答本文観測だけで判定しません。

別のパソコン幅・モバイル幅のケースでは、購読・原文取り込み・保存の後に画面からクラウド収集を開始します。すべての記事画面を閉じるまで配信元の応答を待機させ、ブラウザのタイマーやテスト専用のアラーム呼び出しを使わず、実際のDurable Objectアラームで収集します。画面を閉じた後の取得結果、Worker再起動後の保持、画面がない間に原文を取得しないことを確認します。同じ一時プロフィールで開き直すと、RSS変更の取り込み・受領確認、変更された本文の取得、選択中の旧本文と保存／既読の保持、更新通知が必要です。明示的に新版を選び、再読み込み後も両方の版を保持します。Googleと配信元の応答だけが固定データであり、実PC電源オフ、ブラウザプロセスやプロフィールの復旧、実際の15分間隔、クラウドの長期運転の検証ではありません。

## 証跡と修正

機能テスト結果は `test-results/browser.json`、失敗時のトレースは `test-results/chromium/` へ保存します。リーダー実行環境の結果は `test-results/reader-runtime.json`、画面と失敗時のトレースは `test-results/reader-runtime/` です。検索テスト結果は `test-results/search.json`、全測定値は `.local-state/search-performance/results/**/measurements.json` です。
これらは後の実行で上書きされます。修正や再実行の前に失敗ログを保持し、必要なJSON・トレースをGit除外のタスク専用ディレクトリへコピーします。コマンド、ランタイム・ブラウザのバージョン、ソースハッシュ、依存の同一性を記録します。未コミット変更のある作業ツリーではコミットだけでは不十分なため、変更・未追跡のソース、設定、テストを含むハッシュ一覧も保持します。

[リーダーの検索条件](browser-rss.ja.md#ローカルの記事検索)に従い、200msの基準を緩めたり、サンプル数を減らしたり、外れ値を捨てたりしません。DB初期読み込みと準備は別計測です。基準コーパスにタグはなく、別の大量タグ付きコーパスでは同じ本文にタグ検索・絞り込みを追加します。いずれも実機スマートフォンの計測ではありません。
失敗時は製品の不具合、テスト制御の不具合、前提条件の不足を区別します。失敗を保持して原因を修正し、影響する検査を再実行します。以前の成功を再利用できるのは、ソース・検査設定・依存・環境・保存証跡が一致する場合だけです。合格するまで無条件に繰り返しません。

CIのWebジョブは既存の静的・単体・ビルド検査の後に、同じ機能・リーダー実行環境・検索コマンドを実行します。チェックアウトしたSHAを記録し、検証開始後の失敗も含めて合成テストの結果と測定値を14日間保存します。アップロード対象に個人DBや一般の `.local-state` 内容は含めません。成果物のアップロードが成功しても、未実行・失敗した検査を受け入れ済みにはしません。今回の変更でネイティブ・Goジョブや必須のワークフロー判定は削除しません。

### ダウンロードしたCI証跡の確認

1つの `browser-validation-<run>-<attempt>` 成果物を専用ディレクトリへダウンロードした後、読み取り専用の検査を実行します。

```bash
node scripts/verify-browser-evidence.mjs ARTIFACT_DIR CHECKED_OUT_SHA FUNCTIONAL_COUNT RUNTIME_COUNT
```

完全なチェックアウト先コミットSHAと期待する件数は、成果物の成功件数ではなく、対象ソースとテスト一覧から指定します。2026-10-30の実行 `41011410353` では `28afde9041b369ab5f95ed85e6910a87268cd9b4 556 4` です。PRの検査では一時的なマージコミットを使う場合があるため、証跡を再利用する前に、そのtreeと対象HEADの一致を別途確認します。このスクリプトが確認するのは成果物に記録されたSHAであり、GitHubの実行の同一性・tree一致・由来ではありません。正確な実行と試行回数の信頼できるダウンロードを使い、ワークフローの結論も別途確認します。捏造された報告や整合的に置き換えられた報告の真正性は証明できません。

報告の欠落・不正、0件、件数・プロジェクト不一致、ケース重複、skip・flaky・失敗を期待する結果、再試行、報告全体のエラーを拒否します。集計値だけでなく個々の結果も確認します。検索は3デザインの両コーパス、維持する記事数・タグ密度、クエリ／絞り込みと競合条件ごと30測定（合計2,700）、成功した書き込みの時刻、全測定と最大値の一致、全測定200ms未満を必須とします。準備時間や測定ファイルの欠落も失敗です。負荷条件やレポーター形式の変更には検査とテストの明示的な更新が必要で、未知の条件を黙って通しません。

成功時は準備時間を分けた6条件の最大値・件数・確認した10ファイルのSHA-256を含むJSONを標準出力へ返します。失敗時は成功サマリーを出さず、非ゼロで終了します。テストの実行や再試行、成果物の変更、認証情報の取得、外部通信、PR承認は行いません。回帰テストは既存の `npm test` とCIのサーバーテストに含みます。正解照合・各クエリ中の書き込み進捗・網羅性は、引き続き元のベンチマークとソースレビューで確認します。証跡の要約を新しい性能測定・セキュリティ監査・独立レビュー・利用者の受け入れとは扱いません。

### 検索の診断

検索失敗の時間内訳が必要な場合は、元の失敗を保存してから `node scripts/diagnose-search.mjs` を実行します。維持済みベンチマークの計測付きコピーを新しい `.local-state/search-diagnostics/run-*/` に作り、元のベンチマーク・アプリ・受け入れ結果は変更しません。同じ隔離ポート・プロファイルで、各デザインの大量タグ630測定すべてを実行し、正解・書き込み進捗・200msの検査も維持します。これは診断実験であり、受け入れではありません。トレースの負荷が加わり、タグなしの基準データは実行しません。

任意の引数でデザインとCPU低速化倍率を選べます。例：`node scripts/diagnose-search.mjs editorial 4`。デザインは `all`（既定）、`studio`、`editorial`、`focus`、倍率は `1`（既定）、`2`、`4` です。ローカルの実験条件であり、同等の実機を表すものではありません。同じポートを使うブラウザ・サーバーテストと同時実行しません。

コピーでは、入力イベントの同期処理時間、残りの描画・正解確認時間、最初のフレームのコールバック時刻、両端の表示・フォーカス状態、圧縮したChromiumトレースを記録します。2回のアニメーションフレームのコールバックは両方とも測定内に残します。トレースにはレンダラー処理・GC・トップレベルタスク・compositor/Viz・レンダラーのスケジューリングを含め、長いアプリ処理とフレームの遅れを区別できるようにします。Paintイベントだけでは画面への提示完了を証明できません。Chromiumの[フレームの流れ](https://github.com/chromium/chromium/blob/main/docs/life_of_a_frame.md)を参照してください。マニフェストはソース・依存・検査設定と生成コピーのハッシュを記録し、終了記録はソースが変わらなかったか、必要なトレースがすべて揃ったかを示します。解析前に `diagnosticError` と `traceDataLoss` を確認してください。圧縮トレースは各128MiBを上限とし、不完全・欠落は診断失敗であって停止がなかった根拠にはしません。元の検査コードとの対応が変わった場合は、負荷を黙って変更せず明示的に失敗します。合成データだけを計測し、個人プロファイル・認証情報・アカウントデータはコピーしません。[PlaywrightのCDPセッション](https://playwright.dev/docs/api/class-cdpsession)を参照してください。

CIの維持済み検索ゲートが失敗した場合、まず通常の成果物をアップロードします。その後、上限4分の別ステップで既定倍率1の診断を行い、キャンセルされていなければ `search-diagnostics-<run>-<attempt>` にトレースを14日間保存します。診断が成功しても元の失敗は失敗のままです。Webジョブ全体はインストール・検査・診断を含めて25分を上限とします。依存パッケージの取得だけに12分33秒かかった記録があり、旧15分制限では機能テスト中に打ち切られました。検索の200ms基準やテストごとの上限は変更しません。キャンセル時は診断のアップロードができない場合がありますが、先にアップロードした通常の証跡は残ります。

## 既存ハーネスへの接続

新たなループ実行基盤や自動approveのレビュー役を作らず、既存の[Goハーネス契約](../harness/README.ja.md)を使います。固定タスク・検査、別実行のレビュー、上限付き修正、操作を再送しない復旧、ハッシュ確認を維持します。
ブラウザだけのタスクでは、上記の個別コマンドを同じ順序で信頼済みの `checks` に選びます。関係する場合はWorkers検査を追加します。検査ごとに操作とログを分け、既存の上限付き診断で失敗を修正へ渡します。`check:browser` はローカルの一括実行用とし、同じタスクで内包する個別コマンドを重複実行しません。

ハーネスは隔離したHOMEと固定PATHを使います。Node/npmの絶対パスと必要なツールチェーンだけのPATHを指定した、信頼済みのローカルラッパーを用意します。そうしないとnpmの子コマンドがNodeを見つけられない場合があります。インストール済みPlaywrightブラウザのキャッシュを `PLAYWRIGHT_BROWSERS_PATH` で明示し、一時HOMEによるブラウザ不足を防ぎます。この前提を満たすために認証情報や個人設定をコピーしません。ラッパーとタスクはモデルの編集範囲外に置き、その同一性を検証条件の記録へ含めます。ハーネスの `freeze-task` でラッパーと関係する検査・設定を `protectedFiles` に明示します。作業ツリーのコードハッシュの対象外も含めて、操作の境界で内容とモードを照合します。これは継続する変更の検出であり、照合の間に元へ戻す一時的な変更を検出したり、依存を自動追跡したりはしません。[検査設定の固定の契約](../harness/README.ja.md#検査設定の固定)に従ってください。

実行前に変更可能なソース、受け入れ条件、レビュー担当、操作数・時間・修正回数の上限を決めます。修正役に検査の編集を任せず、テスト成功からapproveを生成せず、本ガイドからモデル利用や支出の権限を推定しません。オフラインのハーネステストが通るだけで現在のブラウザ実装が独立に受け入れられたとは扱いません。別ブランチにあるネイティブ中心の準備補助機能をブラウザ開発へ一括移植しません。
